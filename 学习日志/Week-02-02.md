# Week 03 — AI Agent 工作流整合与 Web App 开发

## 1. 本阶段目标

在前期完成基础环境搭建和部分功能模块后，本阶段开始将独立开发的功能整合为一个可以通过网页操作的 AI Consumer Insight Agent。

开发重点从单个功能的实现转向完整工作流的组织、真实数据质量控制，以及如何让普通用户直接使用 Agent。

## 2. 本阶段新增的开发内容

### 2.1 设计 Agent 的完整工作流

新增 `orchestrator.py`，用于协调不同模块之间的数据传递与执行顺序。

整个 Agent 的目标流程为：

**产品关键词 → 视频搜索 → 评论获取 → 有效反馈筛选 → AI 分析 → 市场研究报告**

通过 Mock Pipeline 测试了各模块之间的连接，并成功生成结构化 Markdown 报告。

这一阶段让我理解了 Orchestration（工作流编排）的作用：Agent 不只是调用一次大语言模型，而是将多个具有不同职责的模块组合起来，形成可以重复执行的流程。

目前端到端分析流程已通过合成数据测试，但还没有在真实 YouTube 评论上完整运行。

### 2.2 增加消费者反馈质量控制

在设计分析流程时，我发现 YouTube 评论不能直接等同于消费者的真实使用体验。

例如：

- 有些评论只是在评价视频内容。
- 有些评论属于购买前咨询。
- 有些评论讨论产品，但没有实际使用证据。
- 有些评论无法明确判断对应品牌。

因此，开发了 Feedback Qualification 模块，对评论进行分类，并区分产品反馈和视频内容反馈。

同时引入了更谨慎的判断方式：

- 缺乏足够证据时，不强行认定评论者使用过产品。
- 品牌归属不明确时，保留 `unknown`。
- 不将购买咨询直接计入负面评价。
- 样本量不足时，在结果中明确提示 `Insufficient Data`。

这让我认识到，**市场研究 Agent 的可靠性不仅取决于 AI 模型，还取决于输入数据的筛选标准。**

### 2.3 开发 Streamlit Web App

新增 `web_app.py`，将原本需要通过终端执行的部分功能转化为网页交互。

目前用户可以直接在网页中：

1. 输入产品关键词。
2. 搜索相关 YouTube 视频。
3. 从搜索结果中选择视频。
4. 查看通过官方 API 获取的真实评论。

相比终端操作，网页界面降低了使用门槛，也让我开始从普通用户的角度思考产品设计。

开发过程中，我进一步理解了前端界面与后端功能之间的关系：网页负责接收用户输入和展示结果，后台模块负责实际的数据获取和处理。

目前网页使用真实 YouTube 数据进行搜索和预览，但 Qwen 对真实评论的分析尚未开放。

### 2.4 建立真实数据处理接口与安全边界

新增 `real_pipeline.py`，为真实数据接入后续分析模块做准备。

这一阶段重点考虑了几个问题：

**数据可追溯性**

保留数据来源及 `fetched_at` 时间信息，帮助判断反馈是在什么时候、从哪里获取的。

**避免不可靠的自动判断**

真实评论进入系统后，不应自动假设其品牌、使用者身份或分析价值已经得到验证。

**区分技术能力与实际开放的功能**

虽然 YouTube 数据获取模块与 Qwen 分析模块分别可以运行，但真实评论的进一步 AI 分析涉及 YouTube API 的数据使用规则。

因此，目前将真实数据预览与衍生分析功能分开，避免误将尚未验证的流程作为正式功能提供给用户。

我也研究了通过 CSV 中转评论的可能性，了解到数据转换格式并不会改变原始数据的使用要求。

### 2.5 完善自动化测试

随着项目功能增加，单纯依靠手动运行程序已经难以验证所有功能是否正常。

本阶段增加和完善了 Pipeline、Web App 以及真实数据接口相关的测试。

目前项目达到 **172 项离线测试通过**。

自动化测试帮助我检查：

- 模块之间的数据格式是否一致。
- 模拟工作流能否完整运行。
- 真实数据处理接口是否正确保留必要信息。
- 未获授权的分析功能是否保持关闭。
- 网页和后台发生变化后是否影响已有功能。

**学习收获：** 自动化测试不仅用于查找代码错误，也能防止新增功能破坏已经正常工作的模块。

## 3. 本阶段遇到的主要问题

### 3.1 独立模块可以运行，但不代表完整系统可以使用

之前各个功能分别测试成功，但当它们需要形成完整工作流时，还需要统一数据结构、调用顺序和异常处理方式。

这让我认识到，模块化开发虽然提高了复用性，但模块之间的接口设计同样重要。

### 3.2 真实评论不一定代表真实消费者

YouTube 评论数量较多，但评论者不一定购买或使用过产品。

如果直接分析所有评论，可能将视频观看体验、购买意愿和真实使用评价混在一起。

因此，Agent 需要在生成报告前判断评论的相关性与证据强度，而不能单纯依赖 LLM 汇总文本。

### 3.3 数据获取成功不等于分析权限已经具备

这次开发中，我遇到了一个原本没有预料到的问题：即使两个 API 都成功连接，也需要确认数据提供平台是否允许进一步生成 AI 分析结果。

我由此开始了解 API 的使用条款、衍生数据分析权限，以及第三方 AI 数据处理等问题。

这让我意识到，实际产品开发不仅需要考虑技术实现，还需要关注数据来源和产品使用边界。

## 5. 下一步计划

下一阶段将重点放在 **MVP（Minimum Viable Product，最小可行产品）** 的实现。

我希望将 Agent 部署到 `agent.zhienyu.com`，让导师或少量体验者能够直接通过浏览器使用。

接下来需要完成的工作包括：

1. 将当前 Streamlit Web App 部署到服务器。
2. 完善网页交互和 API 调用的稳定性。
3. 继续整合反馈筛选、Qwen 分析和报告生成模块。
4. 确认 YouTube 评论用于 AI 分析的适用权限。
5. 在具备相应权限后，验证完整真实数据分析流程。

现阶段不以商业化为目标，而是希望通过一个可以实际使用的小项目，理解 AI Agent 从开发到部署的全过程。

## 6. 本阶段总结与反思

这次开发让我从关注「某个功能能不能运行」，逐渐转向思考「这些功能能否组成一个真正可用的产品」。

我开始理解，开发 AI Agent 并不是简单地把多个 API 连接起来，还需要解决数据质量、工作流组织、测试、使用权限和用户体验等问题。

相比增加更多功能，我认为当前更重要的是将已有模块整合完善，让 Agent 能够稳定、可靠地完成一项具体任务。

这也是我下一阶段希望重点推进的方向：**从能够运行的技术原型，逐步发展为可以供其他人实际体验的 AI 应用。**
