# Week 04 — Product Insight Agent 功能迭代与市场研究报告优化

**日期：2026.11.04**

## 1. 本周学习目标

本阶段主要围绕 Product Insight Agent 的实际应用价值进行开发和优化。

在之前的开发中，我已经完成了 YouTube API 的基本连接，以及使用 Qwen API 对合成评论进行初步分析的测试。

本次希望进一步完善自动化数据收集流程，并将 Agent 的分析目标从简单的评论情绪分类，逐渐转向消费者痛点、未满足需求和产品改进机会的发现。

## 2. 今日完成的工作

### 2.1 升级 YouTube 多视频评论获取功能

今天确认本地 Streamlit Web App 已能够正常运行，并将原先的单视频手动预览升级为自动多视频评论获取。

目前实现的功能包括：

- 输入产品关键词，自动搜索最多 5 个相关 YouTube 视频。
- 每个视频尝试获取最多 10 条公开顶层评论，合计最多 50 条。
- 支持按视频发布时间筛选最近 3、6 或 12 个月的内容。
- 自动进行评论 ID 去重。
- 保留视频链接、评论内容、发布时间和原始来源。
- 对无评论、评论关闭和 API 请求失败等情况提供提示。
- 评论暂时保存在网页会话内存中，不自动写入本地文件。

这一阶段的提升在于：用户不再需要逐个选择视频，可以通过一次关键词搜索获取多个视频的相关讨论。

目前真实 YouTube 评论仍仅用于获取和预览，尚未启用 Qwen 自动分析。

### 2.2 增加两种市场研究模式

在现有分析模块基础上，新增了两种报告类型：

**Product Improvement Research（产品改进研究）**

主要分析消费者在具体使用场景下遇到的问题，并进一步整理：

- 使用场景（Usage Scenario）
- 消费者痛点（Pain Point）
- 未满足需求（Unmet Need）
- 潜在产品改进方向（Improvement Opportunity）
- 后续验证建议（Validation）

**Competitor Research（竞品研究）**

主要针对不同品牌或型号进行同维度比较，包括：

- 不同品牌的反馈覆盖情况
- 相同功能属性下的正负面评价
- 相同使用场景下的消费者认知差异
- 潜在差异化方向
- 尚需验证的竞争假设

这使 Agent 能够根据不同的商业研究目的组织分析内容，而不是所有研究都生成相同的情绪分析报告。

### 2.3 优化报告内容和证据结构

最初的报告虽然能够展示痛点和改进建议，但存在两种研究模式差异不明显、报告内容重复、商业价值不够突出的问题。

因此，今天继续调整了报告结构。

主要优化包括：

1. 将产品改进研究组织成“使用场景 → 具体痛点 → 需求假设 → 改进方向 → 验证方法”的分析流程。
2. 将竞品研究重点转向不同品牌在相同功能和使用场景下的反馈差异。
3. 将原始评论与分析结论关联，通过 Evidence ID 追踪对应证据。
4. 区分用户明确表达的需求与基于反馈推断出的潜在需求。
5. 在数据不足时明确标注 Insufficient Data，避免根据少量评论形成未经支持的市场判断。
6. 删除重复的通用报告内容，将详细来源和方法说明统一放入 Evidence Appendix。

通过这次修改，我更加理解了市场研究报告不仅需要提供分析结果，还需要解释这些结果来自哪里，以及哪些结论仍然存在不确定性。

### 2.4 扩展离线测试数据

为了更充分地验证两种报告的结构，测试数据从最初的 3 条合成评论扩展到了 41 条。

其中，32 条进入产品使用体验分析，其余数据包含购买咨询、视频内容反馈、品牌归属不明确等情况。

测试数据涉及三个虚构品牌：

- DemoAqua
- DemoPool
- DemoTerra

在报告中，针对泳池清洁机器人的导航与避障、续航、清洁效果、维护、售后支持等属性进行了分析。

例如，部分合成评论提到机器人在泳池台阶附近容易卡住，由此形成“改善特殊区域导航和自动脱困能力”的待验证需求假设。

另一部分评论则表现出相同功能在不同使用环境下可能出现的正反面反馈。

这让我认识到，不能仅根据一条评论的情绪判断产品表现，还需要结合使用场景、产品型号和反馈证据进行分析。

本次开发过程中，Work 曾报告 191 项离线自动化测试通过。后续报告结构又进行了修改，最终版本仍需要重新运行测试确认。

## 3. 今天学到的新知识

### 3.1 数据分析与商业洞察存在区别

Sentiment Analysis 能够告诉我们消费者的态度是正面还是负面，但不一定能解释背后的原因。

相比简单统计好评与差评，更有价值的研究是进一步发现：

- 消费者在什么情况下遇到问题？
- 他们真正希望产品改善什么？
- 是否存在尚未被满足的使用需求？
- 这些信息是否能够帮助企业改进产品或制定营销策略？

因此，我开始将 Consumer Needs Discovery 作为 Product Insight Agent 的重要发展方向。

### 3.2 AI 推断需要有证据支持

在报告优化过程中，我进一步理解了 Evidence Traceability（证据可追溯性）的重要性。

消费者实际表达的内容，与 AI 根据内容推测的潜在需求，并不是同一回事。

例如，“机器人在台阶附近卡住”是用户自述的问题，而“用户希望减少人工干预”属于需要进一步验证的需求假设。

如果无法区分这两者，研究报告就可能把模型推断误认为真实消费者需求。

### 3.3 同一产品属性可能受到使用场景影响

在合成样本中，泳池清洁机器人在不同条件下出现了不同反馈，例如：

- 较大泳池与较小泳池的续航体验
- 平坦池底与台阶附近的导航表现
- 不同污物条件下的清洁效果

这让我意识到，产品评价不应仅围绕品牌或产品属性进行统计，还应该考虑具体的使用环境。

这也是未来将视频内容理解与消费者评论分析结合的重要原因。

### 3.4 自动生成报告不等于完成 AI 分析

今天也明确了当前系统的重要技术边界：

最新版研究报告使用的是人工合成评论、人工标注和 Mock 推断。程序可以自动汇总分析结构并生成报告，但新的消费者需求研究模块还没有经过真实的 Qwen 推理验证。

因此，目前证明的是报告生成流程和数据校验结构能够运行，并不能证明 Qwen 已经能够独立准确识别未满足需求。

下一步需要让模型直接处理未标注的合成评论，再与人工参考答案比较，检查分类质量和推断是否可靠。

## 4. 遇到的问题与思考

目前最大的挑战不再只是让不同模块能够运行，而是如何让 Agent 真正产生有价值、可信的商业洞察。

首先，分析结果需要足够具体。如果报告只是重复用户说过的话，就无法提供明显的研究价值。

其次，分析必须保留适当的不确定性。评论中出现的某个问题不一定代表整个市场的普遍需求，正负面评价差异也不一定证明品牌之间存在真实的性能差距。

最后，AI 分析能力需要通过实际模型推理和人工对照来验证，而不是只依赖 Mock 数据和自动化测试。

这让我对 Agent 开发有了新的理解：不仅要考虑系统是否能够运行，还要关注数据质量、推理可靠性，以及结果能否帮助用户做出更好的决策。

## 5. 下一步计划

1. **验证真实 Qwen 推理能力：** 使用现有合成评论作为输入，让 Qwen 自动进行反馈筛选、痛点分类、需求提取和竞品分析。
2. **进行人工对照评测：** 将 Qwen 生成的结果与人工参考标注比较，检查分类错误、品牌归属、场景识别和无依据推断。
3. **完善商业洞察：** 探索如何将消费者需求进一步连接到产品定位、功能优化和营销沟通建议。
4. **确认数据使用权限：** 继续核对 YouTube 评论用于 AI 分析、第三方模型处理及公开展示的适用要求。
5. **准备网页整合：** 在分析流程经过验证后，将研究报告以更加直观、可交互的形式展示在 Streamlit 页面上。

## 6. 今日总结与反思

今天的开发让我感觉 Product Insight Agent 正在从一个简单的 YouTube 评论收集工具，逐渐发展为具有明确研究目标的 AI 应用原型。

相比最初只关注 API 是否能够连接、模型是否能够输出结果，我现在开始更多思考：研究问题应该如何定义、什么样的数据值得分析、哪些推断能够被证据支持，以及最终报告能否为市场营销和产品决策提供实际价值。

我也逐渐意识到，完成一个 AI Agent 不只是调用大模型生成文字，而是需要把数据获取、数据筛选、分析逻辑、证据验证和结果展示组织为完整的工作流程。

接下来，我希望将重点放在真正的模型推理和分析质量验证上，让 Agent 不只是能够生成一份结构完整的报告，而是能够从消费者反馈中发现值得进一步研究的需求和产品机会。
