# Week 05 — AI Product Insight Agent：从模型分析调试到 MVP 全流程跑通

**日期：2026.11.07**

## 一、本阶段目标

这一阶段最大的目标是让 AI Product Insight Agent 从几个可以单独运行的功能，变成一个能够真正自动工作的系统。

我希望实现的最终流程是：

**用户输入产品关键词 → 自动搜索 YouTube → 获取真实消费者评论 → Python 处理数据 → Qwen 分析评论 → 自动生成 Product Insight Report → 在网页展示。**

用户只需要输入关键词，不需要上传 CSV、JSON，也不需要手动处理数据。

在此之前，我已经完成了部分 YouTube API 接入、Qwen 模型调用和 Python 数据处理功能，但这些模块还没有真正形成完整的用户使用流程。同时，之前的大量工作都在优化单条评论的分析准确性。

这一阶段，我先完成了必要的验证工作，然后重新调整开发优先级：**先实现一个能够完整运行的 MVP（Minimum Viable Product），再逐步提高分析准确性和商业洞察质量。**

## 二、具体做了什么？

### Step 1：完善 Qwen 的评论分析与证据验证

最开始，我发现 Qwen 虽然能够分析消费者评论，但经常出现几个问题。

例如，消费者说：

“My pool cleaner keeps getting stuck.”

Qwen 可能会进一步推断这是导航算法或传感器的问题，但原文并没有提供这些技术原因。

另外，模型有时候会把购买咨询当成使用体验，或者遗漏一条评论中已经出现的正面评价。

为了解决这些问题，我进一步完善了 Python 验证机制。

主要涉及两个文件：

- `evidence_analysis.py`：负责组织模型分析，并检查部分分析结果。
- `real_analysis_schema.py`：负责结构和证据相关的校验规则。

具体做法是：

1. 把原始评论拆分成带有 Evidence ID 的文本片段，例如 `S01`、`S02`。
2. 将这些片段和分析要求一起发送给 Qwen。
3. 要求 Qwen 返回结构化 JSON，而不是一大段没有固定格式的文字。
4. Python 读取模型返回的 JSON，检查字段结构是否正确。
5. 再核对模型引用的 Evidence ID 是否确实存在，以及结论是否有原文依据。
6. 将有依据、需要进一步检查、缺乏证据的结果分开处理。

这个过程让我理解了 **LLM + Rule-Based Validation** 的基本思路。

Qwen 负责理解自然语言，Python 负责执行明确的程序规则和部分证据检查。

不过，我也发现：Python 能够检查引用是否存在，并不等于它一定能理解完整语境。因此验证器不能代替所有语义判断。

### Step 2：尝试改进分析流程，而不只是修改 Prompt

在 Phase 3.11 的多轮实验中，我发现单纯给 Qwen 增加更多指令，并不能稳定解决全部问题。

有时模型能够正确识别正面反馈，却又把产品型号、亲身使用经历或明确需求分类错了。

因此，我尝试过一种 Evidence-First 的分析思路：

先提取原始证据，再进行 Python 验证，最后才生成更高层次的消费者洞察。

例如，一条评论包含：

- 机器人池底清洁效果不错。
- 机器人在斜面容易卡住。
- 用户希望改善某项功能。

这三项应该分别提取和核验，而不是全部混在一段总结中。

同时，我也测试了 Claim-Level Validation，即逐项验证结论。

这样一条评论即使存在某个错误字段，也有机会保留其他独立可信的信息，而不是直接丢弃全部内容。

经过历史响应回放、跨行业测试和不同架构比较，我最终保留了三种思路：

- **方案 A：** 原有的单次 Qwen 分析流程。
- **方案 B：** 先提取证据，再做独立分析。
- **方案 C：** 保留单次调用，但增加有限错误隔离和语境检查。

目前继续使用方案 A 作为基础运行流程，其他方案留作后续改进。

这部分工作的主要成果，是建立了更清晰的证据验证机制，以及认识到分析任务越复杂，模型越有可能遗漏或混淆信息。

### Step 3：用真实评论进行跨行业验证

为了避免系统只适用于泳池机器人，我还进行了一轮跨行业验证。

通过现有 YouTube Data API 获取了 32 条新的真实评论，涉及：

- 泳池机器人
- 无线耳机
- 智能手机
- 软件订阅服务

其中 30 条符合当时的执行配置，实际进行了 Qwen 分析测试。

Python 在这一阶段主要负责：

1. 保存评论原文、来源链接和 Evidence ID。
2. 整理不同产品领域的输入数据。
3. 调用 Qwen 进行分析。
4. 解析 Qwen 返回的 JSON。
5. 根据验证规则判断哪些结论可以保留。
6. 记录每条评论为什么通过或被拒绝。
7. 比较不同验证方案的输出结果。

这轮一共完成了 30 次 Qwen 调用，JSON 解析全部成功，24 条通过 Schema 校验，195 次 Evidence ID 引用均能定位原文。

不过，最终没有任何产品属性事实满足全部正式统计条件。

我发现，问题并不完全是模型分析错误。有些评论明明描述了实际使用行为，Python 的亲身使用识别规则却没有正确识别；有时 Qwen 也会把两个独立的事实合并，或者把产品归属写错。

因此，这一阶段帮助我明确了后续需要优化的地方，但也让我意识到：不能因为这些细节没有全部解决，就一直推迟整个产品的开发。

## 三、最重要的工作：把 MVP 真正连接起来

经过前面的验证，我决定暂时停止持续微调模型，把重点放回整个 Agent 的实际运行流程。

这次主要修改和连接了以下 Python 文件：

| 文件 | 在系统中的作用 |
|---|---|
| `web_app.py` | Streamlit 网页入口，接收关键词并展示结果 |
| `automatic_research.py` | 将数据采集、处理、模型分析和报告生成连接起来 |
| `analysis_control.py` | 控制分析任务、API 调用和预算 |
| `evidence_analysis.py` | 组织 Qwen 分析并验证证据 |
| `research_quality.py` | 整理结果并生成报告展示内容 |

### Step 4：建立用户输入入口

我使用 Streamlit 搭建了网页界面。

Streamlit 是一个 Python Web 框架，可以直接用 Python 创建交互式网页，不需要一开始就单独开发完整的前后端系统。

现在用户可以：

1. 打开 Agent 网页。
2. 输入产品关键词，例如 `Robotic Pool Cleaner`。
3. 确认数据使用说明和本次 API 调用。
4. 点击“开始研究”。
5. 等待系统自动完成后续工作。

这一部分主要由 `web_app.py` 实现。

Streamlit 负责接收输入、触发 Python 的研究流程，并把最后的结果显示出来。

### Step 5：自动获取 YouTube 评论

用户输入关键词后，系统通过 `automatic_research.py` 调用已有的 YouTube 数据采集功能。

例如输入：

`Robotic Pool Cleaner`

Python 会将这个关键词交给现有的 YouTube 官方 API 搜索流程，找到相关视频并获取可用的公开评论。

然后自动进行一些基础处理：

- 整理不同视频返回的数据。
- 去除重复评论。
- 保存评论文字和来源信息。
- 保留视频、评论 ID 等可追溯字段。
- 将数据转换成后续分析所需的统一结构。

这一步最重要的是：**不再需要我手动下载评论文件，然后上传给模型。**

数据采集与处理已经连接到用户输入操作。

### Step 6：Python 自动将数据转换成 JSON

YouTube API 返回的数据需要整理，才能按照统一格式发送给 Qwen。

因此，Python 会把获取的评论转换成内部标准 JSON。

JSON 可以理解成一种结构化数据格式，例如：

```json
{
  "keyword": "Robotic Pool Cleaner",
  "comment_id": "example_id",
  "comment_text": "The cleaner works well.",
  "source": "YouTube",
  "evidence_id": "S01"
}
```

这是格式示意，不是真实运行记录。

相比直接把一大段评论交给模型，结构化数据能够让程序更容易管理评论、来源和证据引用。

这里我理解了 Python 在 Agent 中非常重要的一个作用：

**Python 不一定负责理解评论的含义，但它负责让数据在不同模块之间按照统一格式传递。**

目前系统主要在内存中处理这些 JSON 数据，用户不需要看到或操作中间文件。

### Step 7：自动调用 Qwen 进行消费者分析

数据准备完成后，Python 会自动调用北京地域的 Qwen 模型。

流程大致是：

1. Python 读取已经整理好的评论。
2. 将评论、Evidence ID 和分析提示词组合成模型输入。
3. 通过 Qwen API 发送请求。
4. 接收模型返回的分析结果。
5. 解析返回的 JSON。
6. 执行必要的 Schema 和证据校验。
7. 将结果传给报告模块。

这里涉及两个不同的角色：

**Qwen 负责语言理解与分析。**

例如识别消费者在咨询什么产品、抱怨什么问题、表达了什么需求。

**Python 负责自动化和控制。**

例如调用 API、检查输出、限制费用、处理异常，以及将分析结果传到下一步。

因此，整个 Agent 并不是简单的 Chatbot，而是由 Python 组织多个步骤、使用 LLM 完成特定分析任务的自动化工作流。

当前 MVP 为了优先跑通流程，每次研究会从采集到的评论中自动选择 1 条送给 Qwen。

因此，它已经实现了完整自动化，但还不是多评论汇总分析系统。

### Step 8：自动生成 Product Insight Report

Qwen 分析完成后，`research_quality.py` 会整理结果，并将内容提供给网页。

报告目前主要区分：

**1. 经过严格验证的产品属性事实**

只有符合现有证据与统计准入条件的信息，才能进入正式 Product Improvement Research 属性统计。

**2. 探索性消费者观察**

例如用户在两款产品之间犹豫，或者询问某项功能是否值得购买。

这些内容虽然不一定属于已确认的产品使用体验，但依然可能具有市场研究价值。

**3. 值得进一步研究的问题**

例如消费者比较两款机器人时，究竟最关注哪些购买决策因素。

这类内容作为后续研究方向，而不是直接当作已经证实的市场结论。

报告还会尽量保留原始评论来源，方便使用者回到 YouTube 查看证据。

如果 Qwen 输出无法通过必要校验，网页会说明失败原因，而不是直接把不可靠结果展示成正式结论。

### Step 9：在 Streamlit 网页中显示报告

完成分析后，系统会将报告返回到 Streamlit 页面。

这意味着从用户角度看，整个操作变成：

**输入关键词 → 点击开始 → 自动运行 → 查看报告。**

用户不需要打开 Python 文件，也不需要手动运行数据清洗或模型分析脚本。

目前报告结果主要保留在网页会话内存中，按现有配置最多保留约 15 分钟，尚未建设长期报告管理功能。

这一步是本阶段最重要的成果：**我第一次真正把分散的 AI、API 和 Python 处理模块整合成了一个可以使用的产品原型。**

## 四、真实运行结果

为了确认系统不只是代码测试通过，我实际使用三个不同产品关键词进行了端到端运行。

| 产品关键词 | 获取评论数 | Qwen 调用 | 最终结果 |
|---|---:|---:|---|
| Robotic Pool Cleaner | 30 | 1 | 成功生成初版报告 |
| Wireless Earbuds | 40 | 1 | 模型返回结果，但反馈分类未通过校验 |
| Smartphone Battery | 50 | 1 | 成功生成初版报告 |
| **总计** | **120** | **3** | **2 次报告成功、1 次明确反馈失败** |

三次测试实际调用 Qwen 共 3 次，合计消耗：

- Input Tokens：2,178
- Output Tokens：993
- 估算 API 费用：¥0.0037284

120 条评论均通过来源字段校验。

其中，泳池机器人测试成功保留了一条关于 Aiper Scuba S1 与 Aiper Scuba V3 AI 的购买咨询，并生成了值得进一步调查的产品比较问题。

手机电池测试则保留了有来源的本人续航体验原文，但模型概括仍标记为待复核。

耳机测试虽然没有成功生成合格报告，但网页能够正确显示失败原因和原始来源，说明系统在分析异常时也有基本的错误处理能力。

**这三个测试最重要的结果，是证实用户输入关键词之后，Python 能够自动完成数据采集、结构化、模型调用和网页结果返回。**

同时也证明了系统可以从不同产品领域获取数据，而不是只能处理泳池机器人。

不过，目前还不能认为它已经能够稳定生成高质量的跨行业商业洞察。

## 五、遇到了什么问题，怎么处理？

### 问题 1：一直在优化模型，却迟迟没有完整产品

之前我把很多时间放在评论分类、证据引用和模型准确性上。

虽然解决了不少问题，但每次修复后仍然可能遇到新的错误。

**我的调整：**

重新区分 MVP 和成熟产品的开发目标。

MVP 阶段首先验证完整流程能否运行，模型准确性和高质量商业洞察可以在流程打通之后继续优化。

但来源真实性、基本错误处理和费用控制仍然必须保留。

### 问题 2：严格验证导致报告经常没有内容

以前的规则主要针对有明确证据的亲身使用体验。

但真实 YouTube 评论中还有很多购买咨询、价格顾虑和产品比较问题。

这些内容虽然不能直接作为真实产品故障统计，但对于市场研究依然有价值。

**我的调整：**

在不降低正式统计标准的前提下，将探索性消费者观察和正式产品属性统计分开显示。

这样可以保留有来源的初步市场信息，同时不夸大它们的可信程度。

### 问题 3：部分 Qwen 输出无法通过验证

在 Wireless Earbuds 测试中，Qwen 正常返回了结果，但反馈分类没有通过 Python 校验。

**当前处理：**

网页能够显示具体失败状态和原始来源，而不是让系统静默失败或展示没有通过校验的报告。

后续仍需要提高模型分析结果与验证规则之间的兼容性。

### 问题 4：项目实验文件过多

之前多轮调试产生了大量报告、JSON、测试记录和临时文件。

我对项目进行了一次基础整理，删除可重建缓存，并将部分历史结果压缩归档。

同时保留了核心代码、环境依赖、历史原始响应和重要验证记录。

这让我认识到，软件开发除了写代码，也需要管理文件结构、运行环境和历史版本。

## 六、本阶段的技术收获

通过这次开发，我对 Python 和 AI Agent 有了更具体的理解。

**1. Python 可以作为整个 Agent 的协调中心。**

它负责把用户输入、API 数据采集、数据处理、LLM 调用和报告生成连接起来，而不是只用来做数据分析。

**2. API 是不同系统之间连接的接口。**

YouTube API 负责提供原始数据，Qwen API 负责执行语言分析。Python 通过这些接口把两个外部服务整合到一个产品里。

**3. JSON 是不同模块之间的数据桥梁。**

统一的数据结构使评论、分析结果和证据引用能够在不同模块间传递，也方便程序检查模型输出。

**4. Streamlit 可以快速将 Python 程序变成可操作的网页。**

相比一开始开发复杂的前后端架构，Streamlit 让我可以先验证产品核心功能和真实用户操作流程。

**5. LLM 的分析能力和 Python 的验证能力应该配合使用。**

模型擅长理解复杂语言，但可能出现不准确的推断。Python 能够执行确定性检查，却也可能因规则过于严格而遗漏有价值的信息。

两者结合可以提高系统的可控性，但不意味着所有语义问题都能自动解决。

**6. 先完成端到端 MVP，再逐步优化产品。**

这是我这一阶段最重要的产品开发收获。

一个完整、可运行但尚待优化的产品，比长期停留在独立模块调试更有助于我发现真实用户流程中的问题。

## 七、目前完成了什么，下一步做什么？

目前已经完成了：

- Streamlit 网页关键词输入。
- YouTube 官方 API 自动获取评论。
- Python 自动去重及 JSON 结构化。
- Qwen API 自动分析。
- Evidence ID 来源追溯和基础验证。
- Product Insight Report 自动生成和网页展示。
- 基础预算控制及异常提示。
- 三个产品关键词的真实端到端测试。

**MVP 的基本自动化流程已经成功跑通。**

但目前每次研究只会自动分析其中 1 条评论，因此还无法根据大量评论生成真正全面的消费者洞察。

### 下一阶段计划

接下来优先实现 **Multi-Comment Analysis（多评论综合分析）**。

也就是：

用户输入关键词后，Agent 不再只挑选一条评论，而是自动分析多条不同消费者的反馈，再将结果整合成一份报告。

主要改进方向包括：

1. 支持多条评论的批量分析与费用控制。
2. 将类似的消费者痛点和需求进行归类。
3. 区分真实使用问题、购买顾虑和潜在需求。
4. 识别不同评论中反复出现的主题，并标明实际证据数量。
5. 生成更有商业价值的产品改善与竞品分析内容。
6. 改善报告排版、网页体验和分析稳定性。

后续再继续提高模型准确性、跨行业适应能力及完整报告的可信度。

## 八、本阶段总结

这一阶段最大的突破，不是又增加了多少 Python 测试，也不是 Qwen 的某个分类指标提高了多少，而是我真正完成了 AI Product Insight Agent 的第一次端到端 MVP 运行。

之前，我开发的是几个独立功能：YouTube 数据获取、Python 数据处理、Qwen 分析和报告验证。

现在，我已经把它们连接成了一个自动化系统。

**用户只需要输入一个产品关键词，Agent 就能够自动获取真实评论、进行 AI 分析，并在网页生成带来源的初步消费者洞察报告。**

这让我从单独理解 Python、API 和 LLM 的使用，进一步学习了如何将这些技术整合成一个实际的 AI 产品。

接下来，我希望把这个能够运行的原型，逐步发展成一个真正可以帮助企业理解消费者需求、发现产品改进机会的 AI Agent。
