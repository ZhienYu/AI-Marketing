# Week 05 — Product Insight Agent 真实 AI 分析与证据验证

**日期：2026.11.05–11.06**

## 1. 本周主要目标

这次主要想把 Product Insight Agent 从单纯收集 YouTube 评论，推进到真正使用 AI 分析消费者反馈并生成市场研究报告。

之前已经搭建了 YouTube API、Qwen 和报告生成模块，但这些功能还没有利用真实的 YouTube 评论完整运行过。

所以这次主要围绕三个问题展开：

1. 如何使用 Python 把 YouTube API 获取的数据自动传递给 Qwen？
2. 如何让 Qwen 正确识别消费者的使用体验、产品痛点和需求？
3. 如何保证 AI 生成的研究结论真实、有证据支持，并能被程序稳定处理？

## 2. 具体开发过程

### Step 1：连接 YouTube API 和 Qwen，实现自动化数据处理

首先将之前独立开发的数据获取、AI 分析和报告生成模块连接起来。

**具体流程：**

1. 用户在 Streamlit 网页输入产品关键词，例如 `Robotic Pool Cleaner`。
2. Python 调用现有 YouTube Data API 搜索功能，获取符合关键词的视频。
3. 根据视频发布时间筛选最近 6 个月的内容。
4. 从最多 5 个视频中，每个尝试获取最多 10 条公开评论。
5. 获取评论正文、Comment ID、Video ID、发布时间、视频标题和来源链接。
6. Python 对数据进行整理、去重和格式检查。
7. 将结果转换成统一的 JSON 数据结构。
8. 在符合数据使用条件时，将数据交给 Qwen 分析，再传递给报告模块。

**Python 是怎么做的？**

YouTube API 返回的是结构化数据，但不同接口的数据格式并不完全相同。

因此，需要 Python 将视频信息和评论信息整理成统一的结构。

例如，一条评论的数据可以表示成：

- `comment_id`：评论唯一编号
- `video_id`：对应的视频编号
- `text`：评论原文
- `published_at`：评论发布时间
- `source_url`：原始评论链接

Python 可以使用字典（Dictionary）保存一条评论，用列表（List）保存多条评论，然后整理成 JSON 兼容的数据结构。

同时，利用 Comment ID 检查重复数据，利用 Video ID 保证每条评论可以对应到正确的视频。

所有转换都在后台自动完成，不需要用户下载或上传 CSV、JSON。

**实现结果：**

首次网页测试成功获取 5 个视频、40 条真实评论，全部通过字段校验，没有发现异常。之后的一次运行又获取了 50 条有效评论。

这一阶段让我理解了 API Integration 和 Data Pipeline 的基本概念：从外部获取数据，通过 Python 自动清洗和整理，再传递给后续程序。

### Step 2：配置 Qwen API 和费用控制

接下来开始准备真正调用 Qwen。

主要完成了：

1. 固定 Qwen 模型版本 `qwen-plus-2025-12-01`。
2. 使用阿里云北京地域的 API Endpoint。
3. 关闭思考模式，控制模型输出长度。
4. 设置输入和输出 Token 限制。
5. 设置调用次数和费用预算。
6. 禁止失败后无限重试，每次付费运行需要确认。

**Python 是怎么做的？**

Python 负责构建发送给 Qwen 的请求，包括模型名称、分析指令、评论数据和输出格式要求。

Qwen 返回结果后，Python 再读取响应中的 JSON 内容和 Token 使用量。

另外，在请求发送前，程序会先检查剩余调用次数和预算。如果不满足要求，就拒绝继续调用。

这种方式将模型调用与费用控制分开，避免 Agent 在出现错误时持续消耗 API 费用。

**实现结果：**

完成了真实 Qwen 的 API 配置，并可以记录每次调用的输入 Token、输出 Token 和估算费用。

### Step 3：第一次使用真实 YouTube 评论进行 AI 分析

第一次真正将 YouTube 评论发送给 Qwen，选择的是一条 Aiper 泳池机器人的使用反馈。

消费者表示自己试用了两款 Aiper 产品，但机器人会卡在泳池排水口和坡面过渡处。

Qwen 成功返回 JSON 分析结果，但出现了几个问题：

- 漏掉 Aiper 品牌。
- 把实际使用经历错误归类为购买咨询。
- 虽然找到了痛点，但不同字段内容不一致。
- 没有很好地区分明确需求和潜在需求。
- 部分字段不符合程序规定的格式。

**Python 是怎么检查这些问题的？**

模型返回 JSON 后，Python 需要做 Data Validation（数据验证）。

例如，程序会检查：

- 必需字段是否存在。
- 字段类型是否正确。
- 情绪和产品痛点是否存在明显矛盾。
- 原文引用能否在评论中找到。
- 模型是否输出了不符合规则的分类。

这里开始接触 JSON Schema 的概念，也就是规定 AI 必须按照什么结构返回数据。

**实现结果：**

第一次成功完成真实 YouTube 评论到 Qwen 的调用，但模型输出未通过全部业务校验，暂时不能直接生成有效报告。

### Step 4：优化消费者反馈分类和需求识别

针对第一次测试的问题，修改了 Qwen 的 Prompt 和分析数据结构。

主要调整：

1. 支持一条评论同时具有多种类型，例如实际使用体验和购买咨询。
2. 品牌和型号识别必须有评论原文作为依据。
3. 区分消费者痛点、明确需求和潜在需求。
4. 潜在需求必须标记为 AI 推断。
5. 统一不同字段里的情绪、痛点和产品属性。

第二次测试中，Qwen 已经能够正确识别 Aiper、负面使用经历以及消费者需求。

但是，又发现模型会在多个位置生成略有不同的痛点内容，导致数据不一致。

因此，进一步简化了 JSON Schema。

**技术思路：**

不再要求 Qwen 在多个字段里重复写同一个痛点，而是让 Qwen 只输出一次核心事实。

Python 再根据这份事实数据，生成分类统计、产品属性和报告需要的结构。

这样可以减少模型重复生成内容，也避免同一个痛点在不同模块中出现不同版本。

### Step 5：增加安全规范化和质量分级

第三次真实测试中，发现 Qwen 有时会把 Fact ID 输出为数字，而程序要求字符串。

例如，模型可能输出数字 `2`，而内部结构需要 `fact-002`。

于是增加了 Python 的安全规范化功能。

**Python 的处理思路：**

1. 读取 Qwen 返回的 JSON。
2. 检查 Fact ID 是否唯一且合法。
3. 对可以明确转换的数字 ID，生成统一格式的字符串 ID。
4. 同时更新其他字段中引用该事实的 ID。
5. 检查转换后是否存在重复或无效引用。
6. 保留原始模型响应和转换记录，方便追踪。

例如，原始 ID `2` 可以转换为 `fact-002`，其他字段对 `2` 的引用也必须同步转换，不能造成证据对应错误。

这里的关键是：**Python 只修复能够确定的格式问题，不自动修改消费者的实际意思。**

同时，增加了四种质量状态：

- **Valid**：结果通过验证，可以使用。
- **Partial**：部分内容可信，但存在遗漏或需要复核的问题。
- **Invalid**：核心结构或证据有严重问题，无法安全使用。
- **Excluded**：评论与研究主题无关，正常排除。

**实现结果：**

之前第三次真实响应中的数字 ID 可以被安全转换，最终保留为 Partial，而不是因为格式错误就完全丢弃。

### Step 6：测试不同类型的真实消费者评论

之前一直分析同一条 Aiper 评论，因此接下来尝试扩大测试范围。

使用了 10 条真实 YouTube 评论，包括不同品牌的使用体验、购买咨询、价格问题、日文评论和无关内容。

每条评论调用一次 Qwen，不自动重试。

**Python 在批量处理中的作用：**

程序按照评论逐条执行分析，并为每条结果分别记录：

- Comment ID 和来源
- Qwen 返回内容
- 质量状态
- 校验失败原因
- Token 使用量
- 估算费用

如果其中一条评论分析失败，程序会保留错误记录，但不因此丢失其他评论的处理结果。

这让我理解了 Error Handling（错误处理）的作用：在自动化程序中，不能假设每次 API 调用和模型输出都会成功。

**测试结果：**

10 条评论中：

- Valid：3 条
- Partial：0 条
- Invalid：7 条

但三个有效结果全部属于购买咨询，没有真实产品使用体验成功进入报告统计。

进一步检查发现，部分评论其实被 Qwen 正确理解了，却因为引用格式错误而被拒绝。

### Step 7：发现原文引用问题，重新设计 Evidence ID 机制

这是本次开发中最重要的一次调整。

之前的方式是让 Qwen 在生成分析结论的同时，复制对应的消费者原文。

但实际测试发现，大语言模型经常会不自觉地修改原文。

例如：

- Dolphin 评论中，模型把两个空格改成一个。
- 回充失败评论中，模型把 `pull` 改成 `pool`。

虽然模型可能理解了消费者的问题，但这些修改导致引用与原文不一致。

因此，决定让 Python 负责保存和管理原文，让 Qwen 只负责理解内容。

新的设计叫作 **Evidence ID（证据编号）机制**。

**Python 具体怎么做？**

1. 首先保存完整的 YouTube 评论原文。
2. 将评论划分为若干段，例如 S01、S02、S03。
3. 为每个片段记录在原文中的起始和结束字符位置。
4. 建立证据编号与原文片段的对应关系。
5. 将编号后的片段提供给 Qwen。
6. Qwen 分析消费者痛点和需求，只返回对应的 Evidence ID。
7. Python 根据 Evidence ID 找到原始评论片段。
8. 检查证据是否存在、是否属于这条评论，以及是否支持对应结论。
9. 最终由 Python 将原文证据与 AI 分析结果一起放入报告。

这里涉及一个重要的 Python 技术：**String Slicing（字符串切片）**。

例如，如果原始评论保存在 `comment_text` 中，程序记录了某个片段的起止位置 `start` 和 `end`，就可以通过 `comment_text[start:end]` 取得对应原文。

这种方式不会要求 Qwen 再次输入原文，因此能够保留原始空格、标点和拼写。

另外，可以通过 Python 的字典建立类似 `S01 → 原文片段及位置` 的映射关系，再根据 ID 快速查找证据。

**实现结果：**

升级到 `real-analysis-4` 契约，完成 282 项离线测试。原文引用失真的问题得到明显改善。

### Step 8：验证 Evidence ID 在真实 Qwen 分析中的表现

完成 Evidence ID 后，又选取了 5 条真实评论进行验证：

- Dolphin 混合使用体验
- 回充失败与退货
- Beatbot / Betta 多品牌评价
- 日文热水适用性咨询
- 无关影视评论

**实现结果：**

这次五条评论的 Evidence ID 都能够对应到原始文字，之前的空格和拼写问题没有再导致引用失真。

日文评论的理解也有所改善，无关影视评论成功识别为 Excluded。

但新的问题仍然存在：

- Qwen 有时不按照 Fact ID 的规定格式输出。
- 部分字段的证据 ID 数量超出限制。
- Dolphin 评论漏掉正面使用体验。
- 回充评论把退货意向当成购买咨询。
- 一些潜在需求被错误地当成明确需求。

最终结果为：

- Valid：0 条
- Partial：0 条
- Invalid：4 条
- Excluded：1 条

这说明 Evidence ID 解决了部分技术问题，但消费者需求分析的准确性和输出稳定性还需要继续改进。

## 3. 目前实现的主要功能

经过这轮开发，Agent 已经能够：

1. 使用 YouTube Data API 自动收集真实评论。
2. 使用 Python 完成数据清洗、去重和 JSON 结构化。
3. 将数据自动传递给 Qwen API。
4. 使用 Prompt 指导模型提取消费者体验、痛点和需求。
5. 利用 JSON Schema 和 Python 校验模型输出。
6. 使用 Python 安全转换部分格式错误。
7. 通过 Evidence ID 关联 AI 结论和原始评论。
8. 对结果进行 Valid / Partial / Invalid / Excluded 分级。
9. 记录模型调用、Token 消耗和分析错误。
10. 在证据不足时生成明确标记限制的报告预览。

目前已经完成真实 API 调用，但还没有成功生成一份具有充分有效使用体验证据的正式产品改进研究报告。

## 4. 这次学到的主要技术知识

这次接触并逐渐理解了以下概念：

| 技术概念 | 我在项目中是如何应用的 |
|---|---|
| API Integration | 连接 YouTube API 与 Qwen API |
| Python Dictionary / List | 整理评论、视频和分析结果 |
| JSON / JSON Schema | 规范数据输入、输出和字段结构 |
| Data Pipeline | 串联数据获取、处理、分析和报告 |
| Prompt Engineering | 指导 Qwen 提取品牌、体验、痛点和需求 |
| Data Validation | 检查字段类型、原文证据和结果一致性 |
| String Slicing | 根据字符位置取回原始评论片段 |
| Evidence Grounding | 让每项研究结论关联具体的原文证据 |
| Error Handling | 防止单条分析失败影响整个批次 |
| API Cost Control | 管理模型请求次数、Token 和费用 |

这次最大的收获是：

**AI Agent 不只是调用一个大模型，而是需要通过 Python 把数据、模型和验证规则组织成一个可靠的自动化系统。**

Qwen 主要负责理解消费者反馈；Python 则负责数据处理、流程控制、证据追踪和结果验证。

以前我认为模型只要能总结出消费者痛点就算成功，现在发现还需要考虑结论是否有依据、数据能否正确传递，以及如何处理模型输出的不确定性。
