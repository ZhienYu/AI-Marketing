# Week 07 — 从真实评论分析到可交互的商业研究 Dashboard

## 一、本阶段的目标

在 Week 06 中，我已经让 Product Insight Agent 初步实现了从产品关键词、YouTube 评论到 Qwen 分析的流程，但也发现一个问题：系统即使能运行、能输出 JSON，也不代表用户能得到有用的市场研究结论。

因此，这一阶段我不再把主要精力放在让验证测试“全部通过”，而是转向一个更贴近用户的问题：**市场研究人员能不能看懂报告、追溯证据，并从消费者评论中发现值得进一步研究的需求、购买考虑和产品机会？**

我的产品定位也更加明确：用户只需要输入产品关键词，Agent 自动获取获准使用的公开评论，在后台完成筛选、结构化分析与证据核对，最终直接展示报告。用户不需要上传 CSV 或手动处理文件。

## 二、从离线报告到真正的自动化研究（Phase F1–F3）

我先制作了独立的 Business Report 可视化预览（F1），把研究摘要、需求与痛点、购买考虑、产品讨论、商业机会和原文来源组织成不同模块。这里我学到的第一点是：**页面展示了真实 YouTube 评论，并不意味着分析内容一定来自真实模型**。F1 的部分洞察由人工构造，所以必须明确标记为 Demo，不能冒充 Qwen 的真实研究结果。

随后在 F2 中，我把新版报告连接到现有的关键词 → YouTube 采集 → 评论选样 → Qwen 批次 → Python 校验 → Dashboard 流程，没有另外增加一轮商业综合模型调用。第一次真实 Air Purifier 运行中，系统采集 24 条评论、提交 10 条、最终只有 6 条进入定性报告，正式属性统计仍为 0。报告可以生成，但出现了笼统的“其他选购疑问”、把 Acer 笔记本当成净化器竞品、把营销批评当成产品体验等问题。

F3 的工作重点因此变成了定位错误来源，而不是单纯美化卡片。修复后，报告能更准确地区分产品类别与型号、营销观点与亲身体验、购买咨询与实际购买，也不再强迫不充分的证据生成商业机会。

**我的收获：** 一个 AI Agent 的质量需要分层判断。原始评论、模型解释、Python 校验和前端展示都可能出错；最终报告有问题时，不能简单归咎于大模型。

## 三、让一条评论中的多个信息都被看见（Phase G–H）

在之后的 Air Purifier 测试中，我注意到一条评论同时提到了 **180 平方英尺的房间、Xiaomi 与 Mijia 两款候选型号，以及滤芯费用**，报告却主要显示“价格与预算”。这说明不只是评论太少，而是信息在分类和报告映射中被压缩了。

Phase G 开始允许同一条评论支持多个主题，同时按独立评论 ID 去重，避免因为一条评论同时谈到面积、型号和费用，就错误地算作三个消费者。报告的 Executive Summary 也从重复主题名称，转向解释消费者在做什么决策、对企业可能有什么启示。

我还开始认真思考评论规模。最初每轮最多分析 10 条评论；Phase H 增加了 15 条试验模式，最多 4 次 Qwen 请求，预留上限 ¥0.0592，而不是把“4 次调用”误认为只能分析 4 条评论。离线候选集显示，新增分析范围可能带来更多型号咨询和使用问题，但也可能选到价值很低的视频链接。**增加数量不等于自动增加有效洞察。**

真实 Phase H Air Purifier 测试中，采集 27 条、提交 15 条，最终报告只保留 6 条定性来源。起初我怀疑是 Qwen 批次 JSON 失败，但进一步审计发现：四个批次都成功解析，15 个模型条目完整返回；实际有 9 条 `Partial`、6 条 `Invalid`，还有不少可读的消费者信息在 Python 和报告层被丢掉。

这次经历让我意识到：只看“最终留下多少条”不够，还要检查**为什么没有留下**。是原文本身无关、模型理解错误、标签被拒绝，还是展示时丢失了有价值的信息？

## 四、证据保留比整条通过更重要（Phase I）

Phase I 是我认为最关键的一次质量提升。我让系统在严格保留正式属性统计门槛的同时，把评论里**能够独立由原文确认的信息**拆开保留，而不是一个模型标签出错就把整条评论都删掉。

例如：

- 有人说“不需要额外 App 反而是卖点”，这应当是**正面的使用偏好**，不能写成软件故障或修复需求。
- 有人说已经买了 Mijia，又提到滤芯购买与费用；即使 Qwen 错把它标成“购买咨询”，购买自述和耗材费用依然可以分别核对。
- 有人在 Philips、Mighty 2、Vital 200S，或 Cuckoo 与 Xiaomi 之间询问选购意见；可以保留多个候选型号，但不能凭咨询就断言哪一款性能更好。
- 有人已买 Winix 用于卧室，另外想寻找除尘更强的型号；必须把**购买事实、使用场景和新的选购需求**分开，不能编造购买原因或净化效果。

用相同的 15 条真实评论和同一批历史 Qwen 响应离线回放，进入定性报告的来源数从 **6 条提高到 12 条**。此前完全遗漏的 6 条恢复了可核对线索，另有 4 条已展示但失真或缺项的评论得到改善。与此同时，模型校验结果仍是 9 `Partial`、6 `Invalid`，正式属性统计仍是 0。这意味着提升的是**证据利用与报告覆盖**，不是模型准确率突然变成了 80%。

**我的收获：** 严格控制未经证实的结论，与充分利用原文证据并不矛盾。好的验证机制应该拒绝错误推断，同时尽可能保留真实、独立、可追溯的信息。

## 五、从报告页面升级到交互式 Dashboard（Phase K）

接下来，我把重点从逐条卡片转向更完整的商业研究产品。新版 Phase K 报告开始围绕市场研究人员的阅读习惯组织：**研究摘要、消费者主题、需求与偏好、使用场景、购买决策、产品与竞品讨论、研究启示与商业机会、来源与限制**。

这次我特别重视三个变化。

**第一，多评论综合。** 同一个主题可以关联多位独立评论者，上层主题数量按来源 ID 的并集计算；但不能因为两个消费者都说“断音”，就假设发生原因、设备或使用场景相同。

**第二，区分不同证据性质。** 个人预算、询价、地区报价、实际成交价、长期耗材成本不应合并成同一类“价格”。已经购买、亲身使用、候选比较和推荐名单提及也应分开。单条评论可以启发“研究方向”，但不能证明市场普遍性。

**第三，改善真实用户的交互体验。** 我们增加了有编号和图标的章节标题、悬浮导航、当前章节高亮、主题图点击筛选、证据编号弹窗、返回顶部，以及桌面双栏与手机单栏布局。用户点击 S01 等证据编号，就能检查原文和来源性质，不必在长报告中来回查找。报告语言也从偏技术审核的话术，改成更自然的消费者发现与商业解释。

在一次较大规模的历史真实研究中，曾出现 **560 条采集 → 78 条提交分析 → 27 条进入定性报告** 的结果。由于相关逐条会话记录没有完整恢复，我不能据此断定所有未保留评论的原因。Phase K 的多评论聚合和新 Dashboard 则主要通过**历史真实原文配模拟分析**、**全合成示例**及离线端到端模拟验证，不能把这些预览说成真实 Qwen 已经生成了同等质量的报告。

正式 Phase K 研究配置已提升到最多 20 个视频、每视频 50 条顶层评论、目标分析 80 条，最多 20 次 Qwen 请求，单轮预留上限 **¥0.2960**。模拟链路用 20 个视频、1,000 条模拟评论、80 条提交和 20 个模拟批次验证了模块连接；它不等于 80 条真实研究已完成。

## 六、工程实践：测试、版本控制和数据边界

经过多轮改动，我也越来越重视可恢复的工程状态。Phase K 的 Dashboard 已完成桌面 1280px 和手机 390px 的浏览器检查，导航、主题筛选、证据弹窗和返回顶部等交互有离线验证。Work 建立了本地 Git 检查点 **`f57fa13`**，包含本阶段的正式功能和相关测试。完整工作区报告 383 项测试通过；单独提交内容的测试为 329 项通过、2 项跳过，另外有 39 项历史回归通过。不同测试口径要分开陈述。

真实评论 ID、API 密钥、授权配置、运行账本、独立的模型评测资料不应混入公开代码提交。尤其要区分 **本地 commit** 和 **已推送 GitHub**：截至这次记录，已经确认本地检查点，不能在没有推送结果的情况下声称远端仓库已更新。

另一个尚未解决的问题是数据保留时间：目前会话从点击“开始研究”算起，最长只保留约 15 分钟。如果分析接近这个上限，最终报告可能没有足够时间查看。已有截止时间与查看窗口的最小修复建议，但本阶段并未确认修复完成。

## 七、我对 AI Agent 开发方式的新理解

这一阶段我最大的改变，是不再只问“代码能不能运行、JSON 有没有通过”，而是问：**系统有没有正确理解消费者？有没有留下原文支持的信息？最后的商业判断能不能帮助用户做下一步决策？**

我也学到了几个实际开发原则：

1. **先确认问题在哪一层，再决定修什么。** 换模型无法自动解决 Python 后处理丢信息的问题。
2. **报告要有商业意义，但不能把假设写成事实。** “值得测试免 App 是否影响选择”是研究启示，不是已经验证的市场需求。
3. **规模扩展要同时考虑信息质量、预算和可靠性。** 多抓取评论并不代表有效发现一定更多。
4. **Demo、历史原文加模拟分析、完整真实研究必须明确区分。** 界面越专业，越要防止用户误把示例当作证据。
5. **产品体验和研究可信度同样重要。** 美观的 Dashboard 能帮助阅读，但证据追踪和准确表达才是产品的基础。

## 八、下一步计划

当前 Phase K 已完成本机正式网页准备，并建立本地 Git 检查点，但 **80 条真实 Qwen 端到端验收尚未完成**。下一步准备在预算与用途授权允许时，以 Wireless Earbuds 为关键词主动发起真实研究，检查多评论聚合、主题归属、商业机会、分析成本和报告稳定性。

验收时还需要记录选样、批次、逐条校验和报告过滤的汇总原因，避免会话结束后只剩“采集多少、最后留下多少”而无法复盘。之后再考虑 Phase J 的公平模型对比：用同一套冻结证据和同一输出任务比较模型自身理解能力，再测试它们经过相同 Python 流程后的报告效果。

**本周的核心收获：Product Insight Agent 已逐步从“能调用 API 的分析脚本”变成“有证据追溯、能解释消费者决策、可以交互阅读的研究产品”。但真正的下一道门槛，是在未见过的新评论和真实大批量运行中，持续稳定地产出可信、有用的商业洞察。**
