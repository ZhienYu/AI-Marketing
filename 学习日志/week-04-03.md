# Week 06 — From a Working AI Agent to Meaningful Consumer Insights

**Project:** AI Product Insight Agent  
**Period:** MVP 1.1–1.4 Phase E（截至 2026 年 11 月 8 日）  
**Previous milestone:** MVP 1.0 — 完成 YouTube → Python → Qwen → Streamlit 的端到端自动化  
**Current status:** MVP 1.3 已完成并提交；MVP 1.4 的商业推理架构仍处于实验验证阶段。

---

## 1. 本阶段的开发目标

上一阶段，我已经实现了 AI Product Insight Agent 的基础 MVP。用户输入产品关键词后，系统可以通过 YouTube Data API 搜索视频、获取公开评论、使用 Python 整理数据，并调用 Qwen 生成初步研究结果，最后在 Streamlit 网页上展示。

但 MVP 1.0 主要解决的是**整个系统能否运行**，还没有充分解决商业研究报告是否真正有价值的问题。

因此，这一阶段我主要希望实现：

1. 从分析单条评论升级为多条消费者评论的综合分析。
2. 改善评论筛选，让有限的模型调用优先分析有价值的内容。
3. 增加消费者需求、购买考虑、竞品讨论和产品改进机会。
4. 验证 Agent 能否适应不同产品行业。
5. 找出报告中不准确、不合理的商业建议是如何产生的。
6. 探索更适合商业分析的 AI 架构，而不只是继续增加 Python 关键词规则。

在开发过程中，我逐渐认识到：**一个能够自动调用 AI API 的系统，不一定就是一个能够提供高质量商业洞察的 AI Agent。**

## 2. MVP 1.1 — 从单条分析升级为多评论研究

### 2.1 遇到的问题

MVP 1.0 每次主要分析一条评论。虽然可以证明完整流程能够运行，但一条评论通常只能反映某位用户的个人观点，无法帮助研究者了解同一产品下的不同需求和讨论主题。

例如，一条泳池机器人评论可能抱怨清洁效果，另一条可能讨论耐用性，还有用户可能关注价格或竞品。只有把多条反馈放在一起，才有可能形成更完整的消费者研究结果。

### 2.2 具体实现

这一阶段改造了多评论研究流程，主要涉及 `Agent/multi_comment_research.py` 等模块。

新的流程是：

**关键词 → 搜索视频 → 获取评论 → 去重和选样 → 分批发送 Qwen → 合并分析 → 生成报告。**

我了解到，调用 LLM 不一定需要每条评论都单独请求一次。可以通过 Python 将多条评论组织成一个批次，并要求模型分别处理批次中的每条评论。

当时设置的主要运行限制包括：

- 每轮目标选取 10 条评论。
- 每批最多 4 条评论。
- 最多进行 3 次 Qwen 请求。
- 单轮保守预算预留上限 ¥0.0444。
- 不自动重试付费请求。

在代码中，还需要确保每条评论拥有独立的 ID 和证据映射，避免模型把不同消费者的经历混在一起。

### 2.3 真实测试结果

使用不同产品关键词进行测试：

| 测试产品 | 采集评论 | 提交分析 | 可用分析 |
|---|---:|---:|---:|
| Robotic Pool Cleaner | 32 | 10 | 4 |
| Wireless Earbuds | 40 | 10 | 7 |

两次测试都能生成探索性的消费者分析，但正式属性统计仍然是 0。

这让我理解了一个重要区别：

**模型能够从评论中提取有用信息，不代表这些信息已经达到正式统计或经过核实的产品事实标准。**

另外，真实调用也暴露了网络超时、批次失败、评论质量参差不齐等问题。

### 2.4 本阶段学到的知识

我进一步理解了 Python 在 LLM 应用中的数据编排作用。

Python 不只是用来发送 API 请求，还需要负责评论筛选、分批、费用控制、结果合并和错误处理。

我也开始理解 Token 与成本之间的关系：

- 输入 Token 来自 Prompt、评论和上下文。
- 输出 Token 来自模型生成的分析内容。
- 模型调用的预算预留不一定等于实际账单。
- 批量处理可以减少请求次数，但必须控制上下文长度，并保证不同评论之间不会混淆。

**这一阶段让我从单次 API 调用，进一步理解了一个完整 AI 工作流的设计。**

## 3. MVP 1.2 — 提升评论筛选与消费者需求识别

### 3.1 为什么要改进筛选

在真实评论中，并不是所有内容都能用于消费者研究。

例如：

- “Great video!” 评价的是视频，而不是产品。
- “Nice test!” 不能证明消费者对产品满意。
- 假设性的规格讨论，不等于真实使用体验。
- 某位用户对一款产品的抱怨，不能直接归因到另一款产品。

如果系统只根据关键词挑选评论，很容易把这些内容当成有价值的用户反馈。

因此，MVP 1.2 开始重点改善评论相关性和需求提取。

### 3.2 技术改进

这一阶段增加和完善了 `Agent/research_focus.py` 等功能。

主要思路包括：

1. 根据当前研究主题判断评论的相关性。
2. 优先关注具体使用体验、明确需求、购买问题和实际痛点。
3. 区分评论者亲身使用、一般观点、产品期待和视频评价。
4. 保留多语言评论中有意义的消费者需求。
5. 允许一条评论中的部分信息可用，而不必因为其他内容有问题就全部丢弃。

这里我学到了一个重要设计思路：

**一条评论不一定只有一个标签，也不一定只能被判断为完全有效或完全无效。**

例如一位用户可能在同一条评论中提到电池续航、价格和使用场景。系统需要理解这些具体表达，而不是只给整条评论贴上一个简单标签。

### 3.3 Smartphone Battery 测试

在手机电池相关测试中：

- 采集 50 条评论。
- 提交分析 8 条。
- 保留 7 条探索性可用分析。
- 正式属性统计仍为 0。

报告出现过一些明显的问题：

- 把对测试视频的称赞当成产品反馈。
- 把假设性续航要求当成真实使用好评。
- 把 RAM 等不相关规格纳入电池主题。
- 未充分利用消费者明确提出的更大电池、快速充电等期待。

随后进一步调整选样和分析逻辑，并通过离线回归检查。

在一次小规模真实验证中，系统成功选中了三条有研究价值的评论，包括第一人称电池使用反馈、对更大电池和快充的明确期待，以及希望大电池与轻薄机身兼顾的表达。

虽然这三条分析仍为 Partial，未进入正式属性统计，但已经能够支持有来源的探索性洞察。

### 3.4 本阶段学到的知识

我认识到，**数据质量不只取决于模型本身，也取决于模型看到了什么数据。**

如果 Python 将低价值评论排在前面，即使使用更强的 LLM，也不一定能生成好的报告。

同时，跨行业产品研究需要共享分析逻辑，但不能直接共享所有产品属性。

例如，手机电池与泳池机器人都涉及性能和用户期待，但具体的技术指标及使用场景并不相同。

## 4. MVP 1.3 — 从评论分类升级为商业研究报告

### 4.1 为什么需要商业分析模块

在之前的版本中，Agent 更擅长告诉用户：

“这条评论属于价格问题。”

“这条评论涉及产品体验。”

但市场研究人员真正关心的是：

- 消费者为什么在意这个问题？
- 不同消费者是否表达了类似需求？
- 哪些品牌被讨论？
- 是否存在竞争产品比较？
- 企业可以从这些反馈中发现什么机会？

因此，MVP 1.3 开始增加商业分析能力。

### 4.2 新增模块和功能

这一阶段主要增加了 `Agent/commercial_insights.py`，并修改 `multi_comment_research.py` 及相关报告展示逻辑。

报告逐渐形成三个主要模块：

**Consumer Insights**

汇总消费者需求、使用问题、购买考虑和评论主题，并按去重后的评论 ID 统计。

**Competitive Discussion**

识别评论提到的品牌和型号，同时区分用户正在使用、曾经购买、计划购买、推荐或只是提及的产品。

尤其需要避免把不同产品的反馈混淆。

**Product Improvement Opportunities**

根据消费者反馈提出值得进一步研究的产品或商业改进方向。

同时保留原始证据引用，不直接把模型建议当成已经证实的市场结论。

### 4.3 真实验证

使用泳池机器人历史评论进行了小范围 Qwen 验证。

4 条评论中，3 条获得可用于探索性分析的 Partial 结果，1 条 Invalid，正式属性统计仍为 0。

新版报告已经能够展示耐用性、价格讨论和产品型号提及等内容，但仍然存在部分角色识别不充分、主题过于宽泛的问题。

MVP 1.3 在完成离线与有限真实验证后，已经提交到 Git。

### 4.4 本阶段学到的知识

我开始区分两种不同的 AI 任务：

**Information Extraction：信息提取**

识别品牌、价格、型号、消费者需求、原始证据。

**Business Reasoning：商业推理**

解释这些信息对消费者行为、产品定位、竞争和商业机会有什么意义。

这两种能力并不相同。

一个模型能够准确提取价格信息，并不代表它能够据此提出合理的市场机会。

## 5. Air Purifier — 发现跨行业分析问题

为了测试 Agent 是否适用于泳池机器人以外的领域，我使用 `Air Purifier` 进行完整的自动化测试。

### 5.1 实际运行结果

| 指标 | 测试结果 |
|---|---:|
| 视频搜索结果 | 5 |
| 去重评论 | 27 |
| 提交模型分析 | 10 |
| 探索性可用分析 | 5 |
| 正式属性统计 | 0 |
| Qwen 估算费用 | ¥0.00619 |

系统能够完成评论采集、选样、模型分析与报告生成，但报告中仍有部分分析不能采用，因此不能视为完整的高质量研究验收。

### 5.2 发现的严重问题

报告中出现了两条明显与原文不相符的商业建议。

**案例一：CADR 被理解为使用时长**

消费者讨论一款空气净化器的 CADR 和价格，其中出现 `702m3/hr`。

但 Agent 给出的建议是测试产品持续使用时间。

**案例二：除尘需求被理解为轻薄设计**

消费者表示自己关注灰尘，希望寻找净化能力更好的产品。

但 Agent 却建议比较机身厚度和重量。

这些问题非常值得重视，因为它们直接影响报告的商业可信度。

### 5.3 代码诊断发现了什么

Work 检查 Python 代码后，发现两条错误的具体来源：

- `702m3/hr` 中的 `hr` 被关键词规则错误匹配成时间。
- `simple things like dust` 中的 `things` 被 `thin\w*` 错误匹配成轻薄相关表达。

更关键的是，这些匹配结果被用于选择固定的商业建议模板。

这意味着：**即使 Qwen 正确理解了原始评论，后面的 Python 报告生成逻辑仍然可能制造错误建议。**

这次诊断改变了我对项目问题的认识。

之前我一直怀疑是不是 Qwen 模型能力不足，但现在我知道，最终报告质量还取决于 Python 规则、数据结构、模型输出和报告生成之间的衔接。

## 6. MVP 1.4 — 重新设计商业推理架构

### 6.1 Phase A：修复属性匹配错误

首先修改了 `research_focus.py` 和相关报告映射逻辑。

修复包括：

- 不再把 `m3/hr` 的流量单位误判为使用时长。
- 不再把 `things` 误判为轻薄设计。
- 继续允许真正的时间、厚度和重量描述正常匹配。
- 检查建议所依据的属性是否与当前主题相符。

同时保留真实错误案例作为回归测试。

这让我理解了为什么软件开发中需要 Regression Testing（回归测试）：修复一个问题时，也需要确认原本正确的功能没有被破坏。

### 6.2 Phase B：建立 Evidence → Insight → Implication

为了避免固定 Python 模板限制分析能力，新增了 `Agent/shadow_business_analysis.py`。

这个模块尝试让模型完成三个步骤：

**Evidence — 消费者证据**

消费者实际说了什么？涉及什么产品、场景和需求？

**Insight — 消费者洞察**

这些反馈反映了什么购买顾虑、产品体验或消费者需求？

**Implication — 商业启示**

企业可以从这些反馈中发现什么值得关注的问题或机会？

新的商业分析先作为 Shadow Report 运行，不直接替换生产报告。

Python 仍然负责验证来源、评论 ID、证据归属和结构。

通过这一阶段，我了解到一种更合理的技术分工：

**Python 负责确定性的数据处理和规则检查，LLM 负责需要理解语境的语言分析和商业推理。**

### 6.3 Phase C：第一次真实 Shadow 测试

使用 3 条独立的空气净化器评论，调用现有 `qwen-plus-2025-12-01`。

实际使用：

- 输入 782 Token。
- 输出 582 Token。
- 估算费用 ¥0.0017896。

Qwen 正确识别了预算除尘需求和噪声顾虑，但遗漏了包含 CADR 和价格评价的评论。

另外，它生成的建议中出现原文没有的价格门槛和研究参数。

当时的 Python 验证器因此拒绝了整份输出。

这一阶段让我认识到：**模型提出的商业建议，不等于消费者表达过的事实。**

例如，用户没有说自己的预算是 SGD 200，模型就不能把这个数字写成消费者的预算限制。

但企业计划调查 50 个产品，可能只是一个拟议的研究设计参数，性质并不相同。

### 6.4 Phase D：改进证据与建议校验

这一阶段建立了 `business-shadow-2` Schema，并进一步完善 `shadow_business_analysis.py`。

系统开始区分：

- Consumer Evidence Facts：消费者原文中的数字和事实性表达。
- Proposed Research Parameters：由研究者拟定、尚未确认的研究参数。
- Unsupported Claims：没有证据支持的产品、价格或消费者断言。

另外，还增加了证据覆盖检查。

如果重要评论没有被模型引用，系统会保留原文，并记录这一遗漏，而不是自动编造新的洞察。

同时，错误建议可以单独被拒绝，不再因为其中一条建议不合格就丢掉所有有效洞察。

离线回放 Phase C 的真实结果时：

- 3 条洞察被保留。
- 3 条原始建议分别被拒绝。
- 未引用的 E001 被识别出来。

这一阶段通过了 322 项主测试和 39 项历史回归。

不过，测试通过证明的是代码按预期执行，不代表模型已经具备可靠的商业推理能力。

### 6.5 Phase E：第二次真实 Shadow 测试

继续使用同一组冻结评论测试现有 Qwen。

实际结果：

- 输入 1,329 Token。
- 输出 1,500 Token。
- 估算费用 ¥0.0040632。
- 返回 `finish_reason=length`。

这意味着模型在达到 1,500 Token 输出上限时仍未完成 JSON。

模型针对三条独立评论生成了六条可见洞察，部分内容重复，消耗了大量输出空间。

同时还存在一些实际分析错误：

- 把购买期待当成真实使用体验。
- 推断消费者愿意牺牲噪声和性能换取低价，但原文没有这种表述。
- 将没有充分依据的价格解释成消费者预算。
- 没有在可见内容中覆盖噪声咨询。

由于 JSON 不完整，这次没有任何洞察或建议获准发布。

这次失败让我意识到：

**Prompt 和 Schema 并不是越复杂越好。**

模型输出字段越多、任务越重，越容易出现重复内容、Token 消耗和截断问题。

同时，增加 Token 上限虽然可能解决截断，却不能自动解决错误推断。

## 7. 本阶段最重要的产品思考

经过多轮测试和讨论，我逐渐发现，我们花了很多时间设计：

- Evidence ID。
- Schema。
- Validation Method。
- Expected Measurement。
- Research Parameters。
- 各种分析状态与验证规则。

这些技术工作对于系统可靠性很重要，但不应该成为最终用户阅读报告的主要内容。

对于市场研究人员来说，真正重要的是：

**消费者需要什么？**

**消费者对现有产品有什么不满意？**

**什么因素影响他们购买？**

**消费者如何讨论不同品牌和竞品？**

**这些讨论反映出哪些潜在商业机会？**

因此，我决定把 Product Insight Agent 的核心定位进一步明确为：

**AI-Powered Voice of Customer & Competitive Intelligence Agent**

它应当帮助企业理解公开消费者讨论中的需求、痛点、购买因素和竞争线索。

下一阶段的报告应重点回答：

1. **Consumer Needs & Pain Points** — 需求与痛点。
2. **Purchase Drivers & Barriers** — 购买驱动与障碍。
3. **Competitor Insights** — 竞品讨论与比较。
4. **Market Opportunities** — 潜在市场机会。
5. **Executive Summary** — 最重要的研究发现及其商业意义。

来源证据仍需可追溯，但可以通过简洁引用和可展开的技术详情展示。

实验设计、测量指标和研究参数不再是默认商业报告的核心任务。

这一变化让我认识到一个更根本的产品原则：

**开发 AI 产品不是为了展示使用了多少复杂技术，而是为了帮助目标用户更有效地完成工作。**

## 8. 本阶段学到的技术与工程知识

### Python 与 LLM 的职责分工

Python 适合：

- 调用和协调 API。
- 清洗和去重评论。
- 选择、分批和组织数据。
- 管理费用与运行限制。
- 验证结构化结果。
- 保留来源和证据映射。
- 生成可展示的数据结构。

LLM 更适合：

- 理解自然语言和上下文。
- 区分消费者实际体验、需求和观点。
- 归纳多条评论的共同主题。
- 解释消费者需求背后的含义。
- 提出有依据的商业研究方向。

我学到，不能单纯依靠 Python 关键词匹配实现跨行业的复杂消费者分析。

### Prompt 与结构化输出

我进一步理解了 Prompt Engineering 不只是告诉模型“应该做什么”。

还需要控制：

- 模型任务的数量。
- 输出字段的必要性。
- 重复信息。
- 输出 Token 预算。
- 证据与推断的边界。
- JSON 的完整性。

Schema 通过只能说明结构满足要求，不能证明分析在语义上正确。

### 软件测试与真实模型测试

我开始更清楚地区分：

**离线测试：** 验证 Python 规则、数据结构和接口行为。

**真实模型测试：** 验证 Qwen 能否在实际任务中准确理解评论、生成合理结论。

**商业价值验收：** 从市场研究者角度判断报告是否真正有用。

这三个层次不能互相代替。

### 多行业适应能力

我的 Agent 不应该只针对泳池机器人或手机电池。

不同产品有不同的技术属性，但都可以共享消费者需求、痛点、购买考虑和竞争讨论等分析维度。

因此，未来更适合采用通用分析框架，并结合当前产品语境理解具体属性，而不是持续增加大量行业专属关键词补丁。

## 11. Personal Reflection

This stage taught me that building a working AI application and building a useful AI product are two different challenges.

At first, I focused heavily on making the system technically reliable: connecting APIs, validating JSON, tracking evidence, and preventing unsupported conclusions. These steps were necessary, but I gradually realized that technical correctness alone does not guarantee business value.

The most important lesson came from the Air Purifier test. Some recommendations were wrong not because the language model misunderstood the comments, but because Python rules incorrectly mapped words to product attributes. Later tests also showed that a model could understand customer needs but still generate unsupported assumptions or overly complex outputs.

These experiences helped me understand the importance of designing the right division of responsibilities between traditional programming and AI reasoning.

More importantly, I began thinking from the perspective of the end user. A market researcher does not primarily want a long list of validation fields or experimental parameters. They want to understand what customers need, what problems they face, how they compare products, and what opportunities a business should investigate.

My next goal is therefore not simply to make the Agent more technically complex, but to make its insights more accurate, focused, and actionable.

**My key takeaway: The value of an AI Agent is not determined by how many tools or rules it uses, but by how effectively it helps users make better decisions.**
